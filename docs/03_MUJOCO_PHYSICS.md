# 03 MUJOCO PHYSICS: Scene and Elements

MuJoCo (Multi-Joint dynamics with Contact) is the engine that brings RoboChess to life. This document explains how the world is constructed and the physics rules that govern it.

## 📄 The MJCF Scene File
The entire world is defined in a format called **MJCF** (MuJoCo XML).
-   **`src/assets/fetch.xml`**: Defines the robot's structure, joint limits, and meshes.
-   **`src/assets/chess_world.xml`**: Defines the chessboard, pieces, lighting, and graveyard. This file is dynamically generated by `scripts/generate_xml.py`.

## 🧩 Core Physics Elements

### 1. Bodies and Geoms
-   **Body**: A logical part of an object (e.g., "The White King"). It has mass and inertia.
-   **Geom**: The actual shape used for collision detection. For example, a Bishop piece has a complex visual **mesh** but might use a simple cylinder **geom** for physical contact to make calculation faster.

### 2. Sites
A **site** is a zero-mass point in space attached to a body. We use them as "magnets" or reference points.
-   **`robot0:grip`**: The exact center point between the gripper fingers.
-   **Piece Sites**: Every chess piece has a site at its base, which the robot uses as its target coordinate.

### 3. Actuators (Motors)
The robot's arm and gripper use different methods for actuation:
-   **Arm Joints**: The arm does *not* use traditional joint actuators. Instead, it uses a **Mocap Weld Equality Constraint**. A mocap (motion capture) body is moved via IK (Inverse Kinematics) coordinates in python, and the MuJoCo engine automatically calculates the physics forces required to keep the arm "welded" to that invisible mocap target.
-   **Gripper**: The gripper uses **Position Actuators** (a PID controller tracking a target width) to squeeze or release pieces with high force constants (`kp="30000"`).

## ♟️ Piece Physics
To make the game playable, we've tuned the physics of the pieces:
-   **Mass**: Pieces are weighted (approx. 0.05kg - 0.15kg) to prevent them from being accidentally blown away by tiny air currents or "jitter" in the solver.
-   **Friction**: Set high on the base of pieces to prevent them from sliding too easily on the board.
-   **Contact Padding**: A tiny invisible buffer around geoms that prevents them from "tunneling" into each other when pushed hard.

## 🏟️ The Table and Graveyard

### The Board Surface
The tabletop is a perfectly flat plane at `Z = 0.40m`. 
-   **Squares**: Each square is a separate geom. This allows us to change their color (e.g., to highlight the last move).
-   **Labels**: Rank (1-8) and File (A-H) labels are actual 3D box geoms rendered on the board edge.

### The Graveyard (Platform)
When a piece is captured, it is moved to a specific "Graveyard" platform.
-   **Platforms**: These are raised blocks (`Z = 0.424m`) located to the left and right of the board.
-   **Counter Logic**: The `GameOrchestrator` keeps track of how many pieces are in each graveyard to place the next captured piece in the next available grid slot.

## ⚙️ The Physics Solver
The simulation runs at a **timestep of 0.002 seconds**.
-   **Substeps**: We run 20 physics steps for every 1 action from the RL policy. This means the robot "thinks" every 0.04 seconds, but the physics is calculated much more frequently to ensure stability.
