## Critical Issues

#### ● CRITICAL #1 — fingers_closed Check Is Inverted — Valid Grasps Always Detected as Failures

In _close_gripper_with_descent (02_low_level_design, motion primitives), the success criterion includes:

```text
# success requires all three conditions:
xy_dist < GRIP_CONTACT_TOLERANCE
piece_to_grip < desired_gap
fingers_closed  ←  max |finger_qpos| < 0.002
```

Finger joint positions are 0.0 when fully closed and ~0.05 when fully open. If the gripper has successfully grasped a piece, the fingers are held apart by the piece at a position equal to the piece's radius — typically 0.010–0.020. The condition max |finger_qpos| < 0.002 means 'fingers almost fully shut, nothing between them.' This is precisely the condition for a failed grasp (closing on air).

The practical consequence is that every successful grasp returns False, triggering the retry path (two more HOME_RESET → approach cycles) before giving up. The arm will never succeed at the CLOSE_GRIPPER_ONLY stage as currently written.

There is also a cascade: StageGripAttachmentCheck fires after a successful CLOSE_GRIPPER_ONLY to verify piece-to-grip distance. Because the inverted check makes 'success' mean 'gripping air', the attachment check would then fail (piece is not close to grip). Two health check violations per grasp attempt.

> **✔ Fix:** Remove the fingers_closed condition entirely. The piece_to_grip < desired_gap check already captures the relevant physical state. Alternatively, invert the condition: a successful grasp means the fingers are NOT at full-open position, i.e. max |finger_qpos| < (GRIPPER_OPEN - some_tolerance).

#### ● CRITICAL #2 — Spare Pieces Excluded from Collision/Damping Caches — Promotion Moves Will Fail

ChessPickPlaceEnv.__init__ builds _piece_mesh_geom_ids and _piece_joint_dofadrs by scanning bodies, but the constructor spec says 'exclude spare'. The set_piece_mesh_collision_enabled and set_piece_active_damping methods both no-op if the piece name is not in cache.

In the first turn after a promotion, square_to_piece maps the destination square to the spare piece name (e.g. 'w_spare_queen_1'). When execute_op is called for that piece in a subsequent turn, set_target calls set_piece_active_damping and set_piece_mesh_collision_enabled on the spare piece name — both silently no-op. The promoted piece will retain idle damping (200 N·s/m) during manipulation and will have collision behaviour left in whatever state handle_promotion set it to.

With damping at 200 during an active pick, the piece barely responds to contact forces. The gripper will push against it, fail to produce relative motion, and the grasp will fail. Promotion-into-active-piece is a guaranteed failure scenario.

> **✔ Fix:** Include spare pieces in _piece_mesh_geom_ids and _piece_joint_dofadrs during __init__. They are hidden below the table at PIECE_HIDE_Z and have no effect on normal play. Removing the 'exclude spare' filter from the body scan fixes this completely.

#### ● CRITICAL #3 — desired_goal Set to Intermediate Waypoints, Not Final Destination — Breaks HER Policy

The TQC model was trained with Hindsight Experience Replay. In that training regime, desired_goal is always the final placement position on the table, and the policy learns to navigate the gripper to the object, grasp it, and carry it to that goal in one continuous episode.

In the current design, set_target is called at each major stage transition with an intermediate waypoint:

```text
# execute_op start:       goal = src_pos  (source square)
# PREHOVER_SRC stage:     goal = [src_x, src_y, Z_SAFE]  (hover above source)
# PREHOVER_DEST stage:    goal = dest_pos  (correct — only here is it right)
```

During PREHOVER_SRC, desired_goal = [src_x, src_y, Z_SAFE] and achieved_goal = piece position ≈ [src_x, src_y, Z_GRASP]. The policy reads: 'the piece is resting on the board and I need to move it 10–15 cm straight up.' This task was never present in the training distribution (you cannot lift a piece without grasping it first). The 70% scripted weight dominates, so this does not cause a crash, but the RL's 30% contribution during approach is computing actions for an impossible sub-task rather than providing navigation guidance.

The correct setup is also the simpler one: set desired_goal = dest_pos once at the start of execute_op and leave it unchanged for the full operation. The HER-trained policy was designed to handle the entire pick-and-place as a unit when given the final destination as desired_goal. This is the only framing in which the 30% RL contribution is actually useful.

> **✔ Fix:** Call env.set_target(op.piece_name, dest_pos) once at the top of execute_op, before the stage loop. Remove the set_target calls from individual stage actions in PREHOVER_SRC and PREHOVER_DEST — they should only update the physics (active damping, collision) without changing the goal field. Add a separate set_piece_active(piece_name) helper that does only the damping and collision update, keeping desired_goal pinned to the destination throughout.

#### ● CRITICAL #4 — Cylinder Hitboxes Allow Rolling — Cube-Trained Policy Does Not Expect This

The TQC model was trained on FetchPickAndPlace, which uses a cube object. Cubes have six stable resting faces and resist lateral displacement when contacted from the side. Chess pieces in this design use cylinder hitboxes. A cylinder has no lateral stability: it can roll freely around its vertical axis when the gripper contacts it even slightly off-centre during CLOSE_GRIPPER_ONLY.

Concretely: _close_gripper_with_descent applies Z-down motion while commanding GRIPPER_CLOSED. Any resulting lateral contact force on a cylinder causes rotation rather than capture. The policy's velocity features (obs dims 14–25) were calibrated against an object that cannot roll. A rolling piece produces angular velocity signals the policy was not trained to respond to, and the piece may slide off the intended square before the gripper fully closes.

This also affects PREHOVER_DEST: _current_carry_xy_offset reads piece-minus-grip XY to compensate carry drift. If the cylinder rolled even slightly during the close, this offset contains rotational artefact and the carry calculation is off from the start of transport.

> **✔ Fix:** Change all piece hitbox geoms in chess_world.xml from cylinder to box. A box geom with half-extents matching the cylinder radius and height gives the same footprint for board collision, cannot roll, and provides flat contact surfaces that match the cube the policy was trained on. The visual mesh geoms remain unchanged.

## Important Issues

#### ● IMPORTANT #5 — Dynamic model.dof_damping Writes Shift Velocity-Feature Distribution

set_piece_active_damping writes to model.dof_damping — the MuJoCo model struct, not the data struct. This takes effect on the next mj_step. Switching from 200 N·s/m (idle) to 0.05 N·s/m (active) is intentional, but it has a less obvious side-effect on the observation:

The RL observation includes linear and angular velocities of the target piece (dims 14–20). In the few timesteps immediately after set_target activates the piece (changing damping from 200 to 0.05), the piece transitions from near-zero velocity to a regime where it responds freely to contact. The velocity features spike at first contact. The TQC model trained on FetchPickAndPlace always saw consistent piece dynamics — there was no damping transition in training. These transient velocity spikes are out-of-distribution inputs.

A secondary concern: model.dof_damping is global state shared by the model struct. If ChessPickPlaceEnv is ever instantiated more than once from the same mj_model reference (uncommon but possible in tests), damping writes from one env affect the other.

> **⚠ Note:** This cannot be fully eliminated without retraining on matched dynamics. As a mitigation: set_target should set the active damping, then call mj_forward once, then run a small 5–10 step physics settle before the first RL query. This lets the velocity features reach a physically consistent state before the policy is invoked, reducing the out-of-distribution spike.

#### ● IMPORTANT #6 — FETCH_POLICY_HORIZON Must Equal Training Episode Length

Observation dim [25] is computed as: 1.0 - elapsed_steps / FETCH_POLICY_HORIZON. The TQC model actively uses this feature to gauge urgency and modulate its exploration-exploitation behaviour near episode end. FetchPickAndPlace-v1 uses a 50-step episode horizon.

A single RoboChess operation runs for several hundred env steps across 13 stages (PREHOVER_SRC alone can run up to RETRACT_STEPS × 3 steps). If FETCH_POLICY_HORIZON is set to, say, 500 to prevent the feature from reaching zero prematurely, obs[25] stays near 1.0 throughout the entire operation. The policy was trained to urgently converge when obs[25] approaches 0, and operates in a different behavioural regime when it does not. Conversely, if FETCH_POLICY_HORIZON is left at 50, the time feature reaches 0.0 after only 50 steps, and remains at 0 for the rest of the operation — the policy 'believes' it has been out of time for hundreds of steps.

> **✔ Fix:** Set FETCH_POLICY_HORIZON = 50 (the training value) and call env.reset_elapsed_steps() at the start of each stage where the RL is active (PREHOVER_SRC, PREHOVER_DEST). This gives the policy a fresh 50-step budget per navigation stage, matching the temporal distribution it was trained on.

#### ● IMPORTANT #7 — robot_qpos[-2:] Is a Fragile Joint-Ordering Assumption

In ObservationReconstructor.reconstruct_obs, gripper state (obs dims 9–10) is built from robot_qpos[-2:] — the last two elements returned by mujoco_utils.robot_get_obs. This assumes the left and right finger joints are always last in the joint array.

The same joints are already addressed by name in get_gripper_finger_qpos() via 'robot0:l_gripper_finger_joint' and 'robot0:r_gripper_finger_joint'. If the XML ever adds a joint, or if a different version of gymnasium_robotics returns joints in a different order, robot_qpos[-2:] silently extracts the wrong values with no error or warning. The RL policy receives incorrect gripper state for every step.

> **✔ Fix:** In reconstruct_obs, use explicit joint name lookups for the gripper state rather than positional slicing. Look up 'robot0:l_gripper_finger_joint' and 'robot0:r_gripper_finger_joint' by name, the same way get_gripper_finger_qpos does. This makes the obs builder robust to XML changes.

#### ● IMPORTANT #8 — RL Policy's Gripper Output Is Always Zeroed — Effectively XYZ-Only

In _compose_guided_action, the final operation before returning the blended action is: 'Zero out gripper dim.' Additionally, every stage that specifies an explicit gripper_target overrides action[3] entirely via set_gripper_target. The result: the RL model's learned gripper behaviour never reaches the environment.

Since the TQC model was trained end-to-end, its policy network produces correlated XYZ + gripper actions — the gripper output is part of the learned policy structure. Zeroing it out in all stages and replacing it with scripted control is effectively using only 3 of the 4 output dimensions the model was trained to produce. The XYZ outputs are also learned in the context of what the gripper is doing, so discarding the gripper signal may slightly degrade the quality of the XYZ guidance.

> **⚠ Note:** This is a deliberate design choice and is not wrong in itself. However, the complexity of the RL blending (70/30 split, alignment check, rl_vertical_only flag) is not proportionate to the benefit — the RL contributes only to XYZ, only at 30% weight, and only when it agrees with the scripted direction. For most stages the scripted action alone would produce identical behaviour. Consider simplifying to pure scripted control for all stages except PREHOVER_SRC/PREHOVER_DEST, where the 30% RL blend might actually improve convergence speed toward the hover targets.

#### ● IMPORTANT #9 — Pick-Failure Retry Should Restart from PREHOVER_SRC, Not HOME_RESET

On CLOSE_GRIPPER_ONLY or LIFT_VERIFY failure, the state machine resets to HOME_RESET. The full retry path is: HOME_RESET → PREHOVER_SRC → PREGRASP_NARROW → DESCEND_SRC → CLOSE_GRIPPER_ONLY. The arm travels all the way home (potentially across the full board) and then all the way back to the source piece.

Each HOME_RESET transit passes over the occupied board with the gripper open. The 3-waypoint routing avoids sweeping directly through pieces, but it still travels further than necessary and is slower. More importantly, on each home-and-back journey, the arm risks disturbing pieces near the transit path. If a grasp has already been attempted once and failed, the piece may have been slightly displaced — subsequent transits through that region compound the problem.

> **✔ Fix:** On CLOSE_GRIPPER_ONLY or LIFT_VERIFY failure: force gripper open, re-read the piece position, rebuild stage targets, then reset stage_index to PREHOVER_SRC (not HOME_RESET). The arm re-hovers above the piece and tries the descent again without leaving the source area. Reserve HOME_RESET as the retry starting point only for catastrophic failures where the arm state is unknown.

#### ● IMPORTANT #10 — Promotion Restores Spare Mesh Geom to contype=2 — Should Be 0

Stage 10 key notes specify that after a promotion swap, the spare piece's mesh geom should be restored to 'contype=2, conaffinity=2'. Every other piece in the scene has its mesh geom at contype=0 by default — mesh collision is disabled and only activated transiently via set_target during active manipulation.

With contype=2 left permanently on the promoted piece's mesh, it will participate in contact resolution for the rest of the game: potentially colliding with the robot gripper or adjacent pieces even when the arm is nowhere near it. This is inconsistent with the collision architecture and could cause phantom contact forces.

> **✔ Fix:** Restore spare piece mesh geom to contype=0 after promotion, matching all other pieces. The cylinder hitbox (contype=1) handles all necessary board and gripper contact. Mesh geoms are for visual rendering only and should remain collision-disabled unless explicitly activated by set_target.

## Minor Issues

#### ● MINOR #11 — use_rl=False with rl_vertical_only=True Is Dead Code

DESCEND_SRC is specified as _move_gripper_to(..., use_rl=False, rl_vertical_only=True). In _compose_guided_action:

```text
def _compose_guided_action(delta, max_cartesian_action, rl_vertical_only, use_rl):
    scripted = np.clip(delta / ACTION_SCALE, ...)
    if use_rl is False or rl_model is None:
        return scripted   # <-- early return; rl_vertical_only is never read
    ...
    if rl_vertical_only:  # never reached when use_rl=False
        ...
```

The rl_vertical_only flag is only read after the early return, so it has zero effect when use_rl=False. An implementing agent will dutifully handle this parameter, write tests for it, and ship code that documents an intent that is never executed.

> **✔ Fix:** Change DESCEND_SRC configuration to simply use_rl=False with no rl_vertical_only parameter. If the original intent was to blend only the Z axis with RL guidance during descent, change it to use_rl=True, rl_vertical_only=True and verify this is safe (the RL may attempt to push the piece sideways via the Z blend).

#### ● MINOR #12 — _close_gripper_with_descent Re-lifts 5 cm Before Descending

_close_gripper_with_descent begins by aligning the gripper above the piece XY at max(grip_z, piece_z + 0.05). At this point in the pipeline the arm has just completed DESCEND_SRC, which already positioned it near the piece. Raising the gripper 5 cm before the final descent wastes steps and briefly moves the gripper away from the object it is about to grasp.

> **✔ Fix:** Add a proximity check at the start: if |grip_xy - piece_xy| < threshold and grip_z is already within a reasonable range of piece_z + 0.05, skip the re-alignment and proceed directly to the closing loop. Only perform the re-lift if significant XY drift is detected from DESCEND_SRC.

#### ● MINOR #13 — Carry XY Offset in PREHOVER_DEST Is a Snapshot

During PREHOVER_DEST, the target position is computed as: dest_pos[:2] - _current_carry_xy_offset(), where _current_carry_xy_offset() = piece_pos[:2] - grip_pos[:2] (if piece is in air). This offset is computed once at the start of PREHOVER_DEST navigation and used as a fixed waypoint for the entire stage.

As the arm moves toward the hover target, the piece's position relative to the gripper may shift (especially with the low active damping of 0.05 N·s/m, which allows the piece to swing under inertia during transit). By the time the arm reaches the computed hover target, the actual carry offset may have changed, and the piece may not be centred over the destination when the arm arrives.

The DESCEND_DEST stage has a lateral correction pass that partially compensates for this. But for large boards where PREHOVER_DEST involves long horizontal transit, the accumulated drift can be significant.

> **⚠ Note:** Consider recomputing _current_carry_xy_offset() at short intervals during PREHOVER_DEST navigation (e.g., every 20 steps) and updating the waypoint accordingly. This makes the hover target a moving target that tracks the actual carry position. Alternatively, accept the existing lateral correction in DESCEND_DEST as sufficient and document this as a known small-error source.

#### ● MINOR #14 — Piece Site Placement in XML Affects Velocity Features

ObservationReconstructor builds obs dims 3–5 (piece position), 14–16 (piece linear velocity relative to gripper), and 17–19 (piece angular velocity) from the piece's named site ('{piece_name}_site'). In FetchPickAndPlace, the 'object:center_of_gravity' site is at the object's centre of mass.

If {piece_name}_site is placed at the TOP of the piece (a convenient grasp point), rather than the centre of mass, the velocity at that site includes contributions from both linear motion AND rotation of the piece (lever-arm effect). For a piece being lifted, a slight tilt produces a large velocity at the tip but a small velocity at the CoM. The policy was trained on CoM-anchored site velocities and will interpret tip velocities as much more energetic motion than they actually are.

> **✔ Fix:** Place {piece_name}_site at the geometric centre of each piece body in the XML, matching the effective CoM position. The gripper still descends to the piece using the physics body position (get_piece_pos reads data.body.xpos) — the site is only for observation construction and should be at the CoM for consistency with training.

#### ● MINOR #15 — Graveyard Counters Are Duplicated — Controller's Copy Is Dead Code

Two separate systems track captured pieces: GameSystems.captured_count (used by GameOrchestrator._get_graveyard_grid_pos during teleport) and ExecutionController._white_graveyard_count/_black_graveyard_count (used by ExecutionController._next_graveyard_pos).

In GameOrchestrator.execute_ops, all graveyard-bound pieces are teleported before execute_op is called. This means execute_op never receives a graveyard destination, so get_pos('white_graveyard') inside execute_op is never called, and _next_graveyard_pos in the controller is never invoked. The controller's two graveyard counters are never incremented and never read.

> **✔ Fix:** Remove _white_graveyard_count, _black_graveyard_count, and _next_graveyard_pos from ExecutionController. They are dead code. Graveyard position computation belongs entirely to GameOrchestrator, which already has a correct implementation using systems.captured_count.

#### ● MINOR #16 — get_square_pos start_y Description Is Inconsistent Across Documents

In 02_low_level_design.md the board origin is described as: 'BOARD_CENTER - [4*SQUARE_SIZE, -4*SQUARE_SIZE]', which gives start_y = BOARD_CENTER[1] + 4*SQUARE_SIZE. The Stage 9 notes in 06_implementation_plan.md write the formula explicitly and are consistent with this.

However, in 02_low_level_design.md the same section says rank increases in the negative Y direction: y = start_y - (rank_idx + 0.5) * SQUARE_SIZE. With start_y = BOARD_CENTER[1] + 4*SQUARE_SIZE, rank 1 ends up at BOARD_CENTER[1] + 3.5*SQUARE_SIZE (high Y) and rank 8 at BOARD_CENTER[1] - 3.5*SQUARE_SIZE (low Y). Depending on how BOARD_CENTER is defined in the XML, this could place rank 1 on the wrong side.

> **✔ Fix:** The implementing agent must run verify_board_mapping.py immediately after implementing get_square_pos and verify that a1 maps to the correct physical corner. Hardcode a single assertion in tests/test_execution_controller.py: assert get_square_pos('a1')[0] == expected_a1_x and get_square_pos('a1')[1] == expected_a1_y, derived from the XML. Do not rely on the prose description alone.

## Stage Simplification

### Current 13-Stage Structure

The current stage sequence is:

```text
HOME_RESET → PREHOVER_SRC → PREGRASP_NARROW → DESCEND_SRC → CLOSE_GRIPPER_ONLY
→ LIFT_VERIFY → PREHOVER_DEST → DESCEND_DEST → OPEN_GRIPPER_ONLY
→ POST_RELEASE_SETTLE → POST_RELEASE_CLEARANCE → RETURN_HOME → FINAL_PLACEMENT_SETTLE
```

### Three Consolidations That Reduce to 10 Stages

None of these changes remove safety checks. They eliminate transitions that add round-trips without adding verification.

#### Merge A: POST_RELEASE_SETTLE + POST_RELEASE_CLEARANCE → RELEASE_AND_CLEAR

POST_RELEASE_SETTLE waits for the piece to settle after the gripper opens. POST_RELEASE_CLEARANCE then raises the arm. Both of these can happen simultaneously: begin raising the arm immediately after the gripper opens (using tolerate_released_piece_jitter=True, which already exists), and check settle conditions after the arm has cleared. The piece settles whether or not the arm is moving above it.

Benefit: eliminates one stage transition and one set of ARM_STAGE_START/END health check calls. The raise-while-settling approach is also physically cleaner — it removes the gripper from proximity to the just-placed piece before physics settling is measured.

#### Merge B: RETURN_HOME + FINAL_PLACEMENT_SETTLE → SETTLE_AND_HOME

RETURN_HOME moves the arm home after clearing. FINAL_PLACEMENT_SETTLE then runs physics steps to verify the final piece position. Since RETURN_HOME failure is already non-fatal (the state machine continues regardless), the final settlement check can begin as soon as the arm starts moving home. The physics timesteps run as the arm travels; by the time the arm reaches home the piece will have settled.

Benefit: the settle wait is no longer a blocking pause — it is interleaved with the arm's return transit, saving wall-clock time in simulation.

#### Merge C: Absorb PREGRASP_NARROW into DESCEND_SRC

PREGRASP_NARROW is a single call to _set_gripper_aperture(PREGRASP_GRIPPER_OPENING) while the arm hovers in place. Its purpose (preventing the open gripper from clipping adjacent pieces during descent) is valid. However, this aperture adjustment can happen at the beginning of DESCEND_SRC, before the first motion step, rather than as its own stage. The arm doesn't need to be stationary while the gripper narrows.

Benefit: removes one full stage and stage-event dispatch. The gripper pre-narrowing still happens but is part of DESCEND_SRC initialization.

### Simplified 10-Stage Structure

```text
HOME_RESET → PREHOVER_SRC → DESCEND_SRC (gripper pre-narrowed at entry)
→ CLOSE_GRIPPER_ONLY → LIFT_VERIFY → PREHOVER_DEST
→ DESCEND_DEST → OPEN_GRIPPER_ONLY
→ RELEASE_AND_CLEAR (settle + clearance combined)
→ SETTLE_AND_HOME (final placement verify + return home combined)
```

## Physics Environment — Additional Notes

### Single Z_GRASP for All Piece Types

get_square_pos returns Z = Z_GRASP for all squares and all pieces. Chess pieces have varying heights if cylinder hitboxes are sized proportionally (pawn ~30 mm, queen ~60 mm). A single Z_GRASP will cause the arm to descend too far for tall pieces or not far enough for short ones.

If all cylinder hitboxes in the XML are standardised to the same height (regardless of the visual mesh), Z_GRASP works as a single constant and this is not an issue. This should be verified explicitly during Stage 6. If hitbox heights vary, get_square_pos will need to accept a piece body name and look up the hitbox height from the model.

### noslip_iterations = 100 Is High

The project overview lists noslip_iterations = 100. This prevents piece drift from contact sliding (important for stability), but at 40 substeps per action step, each action step runs 40 × 100 = 4,000 noslip solver iterations. This is computationally expensive and may slow training and inference significantly. Start with noslip_iterations = 20–30 and only increase if piece drift is observed in the drift_env_test.py script.

### model.dof_damping Shared Reference in Tests

If test fixtures create multiple ChessPickPlaceEnv instances from the same mj_model (e.g., env = ChessPickPlaceEnv(scene_model, scene_data) called twice), damping modifications in one instance will affect the other because model is a shared reference. Test isolation requires either a fresh from_xml_path call per test or explicit damping reset in fixture teardown. The conftest.py fixture spec should note this.

## Implementation Priority Checklist

Address the following in the order listed before generating any implementation code:

- Fix the fingers_closed inversion (Issue #1). This alone will make every run produce retry loops.

- Remove the 'exclude spare' filter from ChessPickPlaceEnv's body scan (Issue #2). Promotion support requires it.

- Change piece hitbox geoms from cylinder to box in chess_world.xml (Issue #4). This is much easier to fix in the XML before any Python is written.

- Set desired_goal = dest_pos throughout execute_op (Issue #3). Refactor set_target into two separate helpers: one for goal, one for physics activation.

- Fix robot_qpos[-2:] to use explicit joint name lookups (Issue #7). One-line change in obs_wrapper.py.

- Add a verify assertion for get_square_pos('a1') in test_execution_controller.py (Issue #16) before any motion code runs.

- Set FETCH_POLICY_HORIZON in runtime.yaml to match the training episode length and document the value (Issue #6).
